## BUG-001 — Stream Deck worker not nested under its brainstorm
- **Status:** SMOKE-TESTING
- **Found:** 2026-07-19
- **Area:** `08-dashboard/components/StreamDeck.tsx`, `07-daemon/src/lex/anchor-tiles.ts`
- **Symptom:** A worker (bridge or PTY) should render slightly nested under its supervising brainstorm tile. It does not, even though the binding is correct everywhere else (Lex tab shows the right supervised worker; the worker terminal window calls out the right worker).
- **Root cause (grounded against the live DB):** nesting at `StreamDeck.tsx:244` is `groups.find(g => g.slug === t.supervised_project_slug)` — an exact, case-sensitive string match between two DIFFERENT slug formats. Tile side `supervised_project_slug` = `project_session.project_slug` = a short name (e.g. `"DevNeural"`). Session side `group.slug` = the `~/.claude/projects/<dir>` name = the full mangled cwd (e.g. `"c--dev-Projects-DevNeural"`). They can never be `===`, so the worker drops to the orphan branch. Case is also unreliable (CC lowercases the drive letter in the dir; the VB-2 mangler `bridge-presence.ts:121` lowercases everything), so slug matching is fragile regardless. Binding is NOT the problem: `project_session.current_session_id` already resolves the exact worker session id (verified: the DevNeural anchor points at this worker's session).
- **Fix:** nest by the authoritative worker **session id** instead of the slug proxy. Tile emits `supervised_worker_session_id` (= `project_session.current_session_id`); StreamDeck nests the group containing that session id and computes orphans the same way. No change to binding.
- **Fixed:** 2026-07-19 (pending live verify on the dashboard rebuild).

## BUG-002 — Voice barge resumes over a real interruption
- **Status:** RESOLVED
- **Found:** 2026-07-19 · **Fixed:** 2026-07-20 (`ebc3abc`, deployed on the 18:36 daemon). Resume mechanism deleted, so the symptom cannot recur.
- **Area:** `07-daemon/src/voice/lex-voice-ws.ts`
- **Symptom:** talk over Lex mid-sentence; audio stops, then RESUMES the remainder ("you pause then continue"). Any non-command barge is swallowed.
- **Root cause:** the resume path put the barged speech back on every noise/echo/finish resolution. Combined with the `chars=0` L1 (BUG-008) always fail-safe-forwarding verbatim, a real barge looked like phantom echo and resumed.
- **Fix (LAYER-1-CONTROL.md baseline, 2026-07-20):** barge is now deterministic and dumb. `resumeBargedSpeech` is DELETED (every call site -> `dropBargeStash`: drop the stash, STAY stopped; the unused closure removed). The main barge forward no longer fires the deferred PTY Ctrl+C (`confirmRealBarge(false)`), so L2 finishes its reply and the full statement stays READABLE as text; only the TTS audio was cut. Emergency stop (panic -> double-ESC) is the only path that truncates L2. The `chars=0` smart L1 ask (`topLayerTurn` + `parseTopLayerReply` + `applyTopLayerControl` + the classify/rethink/finish helpers) is UNWIRED AND DELETED, not gated. `runTopLayerVoiceTurnOnce` now forwards the operator utterance straight to L2. See `docs/spec/LAYER-1-CONTROL.md`.
- **Baseline acceptance (live):** talk over Lex -> TTS stops on sound, never resumes; the full L2/L1 statement is still readable in the transcript.

## BUG-008 — L1 haiku voice-brain returns chars=0 on every ask

- **Found:** 2026-07-20 · **Fixed:** 2026-07-20 (`ebc3abc` deleted the consumer; impact eliminated)

## BUG-009 — Bell still showed telemetry (worker stalled / idle / false needs-you)
- **Status:** SMOKE-TESTING
- **Found:** 2026-07-20 · **Fixed:** 2026-07-20 (awaiting operator restart + live verify)
- **Area:** `07-daemon/src/dashboard/lex-attention.ts`, `pending-prompt-notify.ts`, `routes.ts`
- **Symptom:** the bell/pill kept showing non-actionable telemetry after two prior fixes (67dc213, 63641c0). - **Fix:** stall severity default `alert -> warn` (signal@warn stays on the activity rail, off the bell); `idle_prompt -> notify_class 'signal'` via `pendingPromptNotifyClass` (real permission/elicitation prompts stay `followup` and still bell); removed the catch-all tail-question rule so "Lex needs you" fires only on a yes/no marker or a decision-head question. Existing on-disk rows collapse + age off the bell via the 6h followup/signal TTL. Tests: lex-attention (25), pending-prompt-notify (8), notifications-class-filter (10) green.
- **Note:** the bell now carries only user-set reminders, "Lex needs you" (genuine asks), real permission/elicitation prompts, the cross-inject "never received an inject" followup (operator kept this one), and true `signal@alert` emergencies.

## BUG-034 - Supervisor test_failure re-fires off a stale 2KB transcript tail
- **Status:** SMOKE-TESTING
- **Found:** 2026-09-23 · **Fixed:** 2026-09-23 (with BUG-035, one refactor: `parseJsonlTail` now ties every Bash `tool_result` to its `tool_use` command (`bashResults`, oldest first); `deriveEvents` runs `permission_denied`, `test_failure` and `commit` over those results only, newest first, inside `RECENT_RESULT_MS` (5 min), and latches the fired record's ts per type (`lastMatchTs`) so one result fires once and never again off a re-read tail; a later Bash result that `reportsPass` (N passed, no failed/FAIL/×) clears a red predecessor. Pins in `worker-event-detect.test.ts`: one denial fires once even after the gap, a new denial fires again, a 6-min-old result is history, red then green yields nothing.) Verify live: a real failing run reaches Lex once; the next tick and the green rerun stay silent.
- **Area:** `07-daemon/src/dashboard/worker-event-router.ts` (`detectTestFailure`, :88-94), `07-daemon/src/dashboard/worker-event-detect.ts` (`parseJsonlTail` :106, `pushIfFireable` :258, `DEFAULT_GAP_MS` :172)
- **Symptom:** Lex receives `[supervisor-event] worker=DevNeural-433a2f event=test_failure` with snippet `(no recent activity)` while the worker is healthy, green and committing. Observed 2026-09-23 at 00:55:39.593Z and again at 01:01:56.632Z. Ground truth at both moments: worker session `df70f86c` `active=true`, and its own reruns returned `4 passed (4) / 55 passed (55)` at 00:55:44 and `4 passed (4) / 58 passed (58) tsc_exit=0` at 01:02:02. HEAD advanced across the window (`58fb3cd`, then `0bfb9e7`).
- **Root cause (read from source, not inferred from the symptom):** `detectTestFailure(jsonlTail)` takes a plain string and tests three regexes against it, including `/exit\s+(?:code\s+)?[1-9]\d*/i`. The string it gets is `parsed.snippet`, which `parseJsonlTail` defines as the trailing 2048 bytes of the raw transcript (`tail.slice(tail.length - snippetMaxBytes)`). Nothing in the path carries a timestamp: unlike `detectIdle`, which is handed `now` and `lastAssistantMs` and compares them, `detectTestFailure` has no recency bound and no notion of a later passing run superseding an earlier failing one. `pushIfFireable` gates only on `shouldFire(..., DEFAULT_GAP_MS)` = 30s per event type. So a single real failure re-fires every 30 seconds for as long as its text sits inside the trailing 2KB, regardless of what the worker did after it.
- **Corroborating detail:** the snippet renders `(no recent activity)` because `extractEventSnippet` walks the *meaningful-line* predicate, which the stale failure text has already fallen out of, while the raw-bytes regex still matches it. A `test_failure` whose snippet is empty is therefore the signature of this bug rather than of a quiet worker.
- **Impact:** supervision noise that inverts the signal. Lex must run a full live probe (sessions phase, jsonl tail, git HEAD) to discover the event was already false, and a genuine failure is indistinguishable from the stale echo of a fixed one. Also burns the per-anchor hourly event cap and pushes toward the `killSwitchPerTenMinutes` polling downgrade on a worker that is doing nothing wrong.
- **Fix (not done here):** give the detector the same recency discipline the idle detector already has. Pass the matched line's timestamp and the run outcome, not a byte window: (1) detect against parsed meaningful lines with their `ts`, not `parsed.snippet` raw bytes; (2) ignore a match older than the fire gap; (3) suppress when a later test-runner line in the same tail reports a pass (`N passed` with no `×`/`FAIL`), so a green rerun clears a red predecessor; (4) latch per failure instance the way `PendingSuccessClaim.fired` latches, so one failure fires once rather than every 30s. Verify by replaying a tail that holds a failure followed by a passing rerun: expected zero events.

## BUG-035 - Supervisor detectors match transcript text the worker read or wrote, not commands it ran
- **Status:** SMOKE-TESTING
- **Found:** 2026-09-23 · **Fixed:** 2026-09-23 (see BUG-034: detectors read Bash `tool_result` records only, tied to their `tool_use` by id; Read/Edit/Write payloads and assistant prose never count. Pin: a tail holding a file-read of the detector fixtures plus an Edit carrying them plus an assistant line quoting them yields zero `permission_denied` / `commit` / `test_failure`. The snippet is extracted from the matched tool_use + tool_result lines, so `denied_tool` / `files_changed` come from the command that ran.) Verify live: editing or testing `worker-event-*` no longer fires alarms at Lex.
- **Area:** `07-daemon/src/dashboard/worker-event-detect.ts` (`parseJsonlTail` :106, `deriveEvents` :285-290), `07-daemon/src/dashboard/worker-event-router.ts` (`detectPermissionDenied` :83, `detectCommit` :103)
- **Symptom:** Two supervisor events, `permission_denied` and `commit`, fired at the identical timestamp 2026-09-23T01:24:30.695Z against worker `DevNeural-433a2f`. The worker had run no denied command and made no commit. Ground truth: at 01:24:30.276Z it completed a `Read` of `07-daemon/tests/worker-event-detect.test.ts`, whose line 206 is `it('emits multiple event types from one tail when each detector fires', ...)` and whose fixtures are the literal strings `'Permission to use Bash has been denied'` and `'[master abc1234] feat: stuff
 3 files changed, 9 insertions'`. The reported `files_changed: 3` and `branch: master` were read straight out of that fixture. 0.42s separated the file read from the two alarms.
- **Root cause:** the detectors are regexes over an undifferentiated byte window. `parseJsonlTail` slices the trailing `snippetMaxBytes` (2048) of the raw jsonl and passes that string to every detector. That window contains, without distinction: assistant text, tool_use **input** payloads (the full body of every Edit and Write), and tool_result **content** (the full body of every file Read). Nothing in the path narrows the match to a Bash tool_result, which is the only record type that can evidence a command actually having run. `detectPermissionDenied` matches its phrase anywhere; `detectCommit` matches `/\[(?:main|master|[\w/-]+)\s+[a-f0-9]{7,}\]/` anywhere. So the detector cannot distinguish "the worker ran a command that was denied" from "the worker looked at a string describing a denial."
- **Self-referential severity:** the fixtures that trip it are the fixtures written to test it. Any session that edits, reads or tests `worker-event-*` emits a stream of fake `permission_denied` / `commit` / `test_failure` events to Lex. The work of fixing BUG-034 is itself the trigger, and both bugs burn the same per-anchor hourly cap (12) and push toward the `killSwitchPerTenMinutes` (20) downgrade to polling.
- **Impact:** supervision signal inverts. A fake `commit` is worse than noise because it tells Lex that HEAD advanced when it did not, which is precisely the mis-trust `narrated_success_no_commit` exists to prevent. Lex must run a full live probe (git HEAD, sessions phase, jsonl tail) to discredit every event before acting on it.
- **Fix (not done here):** detect over structured records, not a byte window. (1) Have `parseJsonlTail` keep the parsed records it already walks and expose typed accessors, so detectors receive `{role, type, tool_name, content, ts}` rather than a string. (2) Gate `detectPermissionDenied` and `detectCommit` to `tool_result` records whose originating `tool_use` was Bash, ignoring Read/Edit/Write payloads entirely. (3) Same narrowing for `detectTestFailure`, which composes with the BUG-034 recency fix. (4) Regression pin, and the reason this needs its own fixture discipline: a test that feeds the detector a tail containing a *file-read* of detector fixtures must assert **zero** events. Note for whoever writes it: that test file's own contents will keep tripping the live detector until the fix lands.
- **Related:** [[BUG-034]] shares the root family (raw regex over raw bytes with no structural or temporal awareness). Fix them together; the parsed-record refactor in (1) is the common prerequisite.
